# نقشهٔ راه پروژهٔ SnappFood Customer Experience Intelligence

## هدف و نقطهٔ شروع

یک نمونه‌کار قابل بازتولید بسازیم که نظرهای فارسی را به مسائل مشخص هر فروشنده، روندهای زمانی و خلاصه‌های دارای شاهد تبدیل کند. [مطالعهٔ امکان‌سنجی](FEASIBILITY_DECISION.md) انجام شده است. پروژه به برچسب‌گذاری دستی جدید، API پولی و دادهٔ سفارش وابسته نخواهد بود.

این سند مرجع ادامهٔ کار است. با هر تصمیم یا نتیجهٔ اندازه‌گیری‌شدهٔ تازه، وضعیت مرحله‌ها و دلیل تغییر آن در همین سند ثبت شود.

## مراحل اجرا

1. **تعریف خروجی و دادهٔ ارزیابی:** فهرست موضوع‌ها را به کیفیت و طعم، دما، بسته‌بندی، قیمت، تأخیر، رفتار پیک، حجم غذا و اقلام ناقص محدود کنیم. [ParsiNLU](https://huggingface.co/datasets/persiannlp/parsinlu_sentiment) و [Pars-ABSA](https://github.com/Titowak/Pars-ABSA) را با نسخهٔ ثابت دریافت کنیم. فقط موضوع‌های مشترک را ارزیابی کنیم؛ امتیاز این داده‌ها «ارزیابی خارج از دامنهٔ اسنپ‌فود» نام بگیرد.

2. **نمونهٔ استخراج:** ۱۰۰۰ نظر اسنپ‌فود را با بذر ثابت و به‌صورت طبقه‌بندی‌شده بر پایهٔ امتیاز، سال و فروشنده انتخاب کنیم. یک مدل محلی با خروجی JSON برای هر نظر، موضوع، احساس و عبارت شاهد پیشنهاد دهد. تطابق عبارت شاهد با متن اصلی، ساختار JSON و شناسهٔ نظر به‌صورت قطعی بررسی شود. متن مشتری و خروجی خام مدل وارد Git نشود.

3. **دروازهٔ کیفیت:** یک روش واژه‌محور/TF-IDF را به‌عنوان خط پایه و مدل محلی را روی مجموعه‌های مرجع یکسان مقایسه کنیم. معیارها: F1 هر موضوع و احساس، دقت بازهٔ شاهد، درصد خروجی معتبر، زمان و حافظهٔ پردازش. توافق مدل‌ها روی نظرهای اسنپ‌فود «دقت» محسوب نشود. اگر استخراج موضوع‌های اصلی از خط پایه بهتر نباشد، انتشار نرخ مسائل متوقف شود و نمونه‌کار به جست‌وجو و نمایش نظرهای مستند محدود بماند.

4. **پردازش و محصول نمایشی:** پس از عبور از دروازهٔ کیفیت، برچسب‌های پیشنهادی را با نسخهٔ مدل و تنظیمات تولید ثبت کنیم و مدل کوچک‌تر را برای پردازش حجم بیشتر بررسی کنیم. API و داشبورد، روند ماهانهٔ *برآوردی* مسائل را فقط برای اتصال‌های مطمئن فروشنده و بازه‌های دارای حداقل ۳۰ نظر نشان دهند. هر خلاصه به شناسه و عبارت شاهد نظرهای واقعی وصل شود؛ عددها از محاسبات ساختاریافته بیایند.

## قراردادها و تحویل‌دادنی‌ها

- رکورد استخراج: `review_id`، `aspect`، `sentiment`، `evidence_span`، `label_source`، `model_version` و وضعیت اعتبارسنجی. هر نظر می‌تواند چند رکورد داشته باشد.
- کد در ماژول‌های جدا برای دریافت داده، استخراج، ارزیابی، تجمیع آماری، بازیابی شاهد و API قرار گیرد. منطق محصول به ارائه‌دهندهٔ مدل وابسته نباشد.
- خروجی گیت‌هاب شامل دستور اجرای محلی، نسخهٔ دقیق داده و مدل، گزارش معیارها، نمونهٔ نمایشی بدون اطلاعات شخصی و محدودیت‌های روشن باشد. پاسخ‌دهی خودکار، ادعای اثر علّی و نرخ شکایت به‌ازای سفارش در این نسخه قرار نگیرند.

## آزمون و فرض‌ها

آزمون‌های ضروری، نمونه‌گیری تکرارپذیر، جلوگیری از نشت داده بین آموزش و آزمون، اعتبار JSON و عبارت شاهد، اتصال مطمئن فروشنده، صحت مخرج نرخ‌ها و درست‌بودن ارجاع خلاصه‌ها را پوشش دهند.

فرض اجرایی: پردازش اولیه روی GPU محلی ۸ گیگابایتی انجام می‌شود و مدل محلیِ قابل اجرا روی آن انتخاب می‌شود. هیچ امتیازی روی دیتاست‌های دیگر به‌عنوان دقت مدل روی نظرهای اسنپ‌فود گزارش نخواهد شد. بدون دادهٔ مرجع از خود اسنپ‌فود، محصول در حد نمونه‌کار پژوهشی با برآوردهای شفاف معرفی می‌شود.

- مرحلهٔ اول، قرارداد خروجی و آماده‌سازی مجموعه‌های ارزیابیِ نسخه‌ثابت: انجام شده؛ [روش، شمارش‌ها و محدودیت‌ها](BENCHMARKS.md).
- مرحلهٔ دوم، نمونه‌گیری و اجرای استخراج محلی روی ۱۰۰۰ نظر: انجام شده؛ [روش و نتایج واقعی](LOCAL_PILOT.md). ۸۸۴ خروجی با شاهد معتبر و ۹۸۶ رکورد پیشنهادی پذیرفته شدند؛ کیفیت معنایی هنوز ارزیابی نشده است.
- مرحلهٔ بعد: ساخت خط پایه و مقایسهٔ مدل محلی روی داده‌های مرجع مشترک؛ دروازهٔ کیفیت مرحلهٔ سوم هنوز اجرا نشده است.
