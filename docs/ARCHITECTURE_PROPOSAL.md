# Architecture proposal

Build a modular Python application in one deployable service. Ingestion reads pinned Parquet revisions in batches; validation checks schema, ID uniqueness, date parsing and join coverage. Store curated reviews, vendor mappings, annotations, extracted issues and evidence references in PostgreSQL. Keep Parquet and DuckDB for offline scans and reproducible analytics. A scheduled pipeline computes period aggregates and confidence intervals. FastAPI serves vendor analytics and evidence IDs; a small dashboard consumes that API. Docker packages the service and jobs.

Define provider-neutral interfaces for `AspectExtractor`, `EvidenceRetriever`, `Summarizer` and `EmbeddingProvider`. Local models and hosted LLMs implement those interfaces. The business layer receives structured extraction records, not provider responses. No vector database is required for v1: filter by vendor/time/aspect, then use keyword or PostgreSQL full-text retrieval; add embeddings only if evaluation demonstrates a retrieval gap.

Evidence-grounded workflow: validated aggregate → issue candidate → retrieval of review IDs and exact spans → verify spans and counts → LLM explanation with allowed evidence IDs → post-generation check that every cited ID exists and every number matches the aggregate. Recommendations are phrased as hypotheses/actions, never as causal findings. If verification fails, return structured statistics without a generated explanation.

Observability: structured logs with dataset revision, pipeline run ID, model/prompt version, record counts and failure counts; no customer text/tokens. Monitor input drift, join ambiguity, annotation quality, extraction confidence, evidence citation failures and API latency. Deploy only after privacy review and access controls for raw comments, sender and vendor contact/location fields.

Evaluation gates: aspect/sentiment macro and per-class F1 on external Persian gold benchmarks; span precision/recall where benchmark offsets exist; exact source-span validity; citation existence; numerical consistency; and cost/latency per 1,000 reviews. Without in-domain reference labels or review, SnappFood extraction accuracy, summary faithfulness and unsupported-claim rate cannot be quantified reliably. Generated text should be constrained to verified numbers and retrieved spans, and the UI must identify issue rates as estimates. No production claim should rely solely on LLM self-grading.
